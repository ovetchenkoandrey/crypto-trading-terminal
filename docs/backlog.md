## Достоверность исполнения

### Два таймфрейма: сигналы отдельно от исполнения
**Статус:** в работе, решение принято 25.08.2026.

Сейчас стратегия получает управление на том же баре, на котором проверяются
её ордера, и внутри бара известны только open, high, low и close — четыре
точки, причём **в неизвестном порядке**. Когда бар накрывает и стоп, и цель,
восстановить из OHLC, что случилось первым, невозможно. Сейчас это закрыто
консервативной конвенцией (стопы матчатся раньше лимиток, ликвидация
считается по худшей цене бара), то есть мы гарантированно ошибаемся не в свою
пользу — но это грубо.

Решение: разделить интервал сигналов и интервал исполнения. Сигналы считаются
на выбранном таймфрейме (M15, M20, H1 — **любом**, не только часовом; какой
именно, определим оптимизацией), а ордера, стопы и ликвидация проверяются по
минутным барам внутри него. Шестьдесят баров вместо четырёх точек, и порядок
движения известен с точностью до минуты.

Данные для этого уже есть — датасет минутный, сигнальные бары собираются
агрегацией.

### Тиковое исполнение для финалистов
**Статус:** отложено до отбора стратегий-кандидатов.

Сейчас исполнение идёт по минутным барам (см. «Два таймфрейма» ниже), то есть
внутри минуты порядок движения цены по-прежнему неизвестен. Полная точность —
только на потиковых данных.

Источник: `https://public.bybit.com/trading/{SYMBOL}/` — посделочные архивы
по дням, с 2020-03 для BTCUSDT. Схема: `timestamp,symbol,side,size,price,
tickDirection,trdMatchID,...`, таймстемп в секундах с миллисекундной дробью.
Объём: **43–75 МБ gz на день**, то есть 35–45 ГБ за два года на символ.

Почему не сейчас: прогон по тикам вместо секунд занимает часы, для перебора
сотен комбинаций параметров это неподъёмно. План — прогнать по тикам одну-две
стратегии, уже прошедшие отбор, как последнюю проверку перед демо-счётом.

### Калибровка модели издержек
**Статус:** обязательно до того, как верить цифрам прогонов.

Три числа в модели правдоподобны по порядку величины, но не измерены:
- вероятность исполнения лимитного ордера (сейчас 0.6) — самая влиятельная
  ручка, одна переворачивает результат сеточных стратегий в разы;
- множители мёртвых часов (×1.75) и выходных (×2);
- частота отказов (базовая 0.001, потолок 0.25) — вероятно занижена.

Чем калибровать: минутные срезы глубины Binance (`data/futures/um/daily/
bookDepth/`, с 2023-01, ~350 МБ за два года) и бесплатные семплы Tardis
(настоящий L2 за первое число каждого месяца — 24 полных дня за два года).

### Частичные исполнения
Ордер сейчас исполняется целиком или никак. Для крупного рыночного ордера это
оптимистично (реально часть прошла в коридоре, остаток отменился), для
остального — пессимистично. На депозите 1000 USDT влияние мало, при
масштабировании выстрелит.

### Спред в бэктесте нулевой
`barAsTicker` отдаёт `bid = ask = close`, поэтому модели проскальзывания
`spread_pct` и `volume_impact` в бэктесте молча дают ноль. Пользователь
выберет «реалистичную» модель и получит идеальные филлы. Нужен либо синтетический
спред из волатильности бара, либо запрет этих моделей в бэктесте.

### Стресс-тест издержек не действует на лимитные стратегии
**Статус:** дыра в критерии приёмки, обнаружена первым же реальным прогоном.

Критерий «стратегия выживает при удвоении проскальзывания» для чисто лимитных
стратегий не проверяет ничего: в движке проскальзывание применяется только
к рыночным и стоп-ордерам, а лимитка исполняется по своей цене. Прогон
сеточного бота под стрессом ×2 дал цифры, совпадающие до последнего знака.

Для индикаторных стратегий с рыночными входами критерий работает. Но для
лимитных нужен отдельный вид стресса — ужесточение вероятности исполнения
и очереди, а не множитель проскальзывания.

### Нет метрики пропущенных исполнений
Лимитка, которую не пробила очередь, остаётся в книге и не увеличивает
счётчик отказов — это правильное поведение, но означает, что вопрос «сколько
раз нам не налили» остаётся без ответа. Нужна отдельная метрика касаний
уровня, не приведших к исполнению: для сеточных стратегий это ключевой
показатель достоверности.

### Проскальзывание симметрично
Покупка в ралли и продажа в ралли стоят одинаково, хотя крыть по потоку
дороже. Направленного компонента (order flow imbalance) нет.

### Фандинг от цены закрытия
Если в событии фандинга нет mark price, платёж считается от close бара.
В тренде занижает платёж по растущей позиции. `fundingEventsFromBybit`
mark price не заполняет.

## Архитектура

### Два матчинг-движка
`src/lib/paper/engine.ts` и `src/lib/execution/backtest/BacktestVenue.ts` —
скопированы друг с друга и уже разошлись в поведении. Каждое улучшение
приходится делать дважды, расхождения будут накапливаться. Кандидат на
выделение общего чистого ядра `matchAndApply(state, order, price, fees)`.

### Прогон в Worker
Цикл прогона синхронный и блокирует интерфейс. На годе минуток (~525 тысяч
баров) вкладка «Тестер» повиснет. Движок почти чист от глобального стора —
зависит только через `bots/registry` → `eventBus`.

### Колоночное чтение датасета
`readRange` за два года материализует около миллиона JS-объектов, ~100 МБ
хипа. Для разовой загрузки нормально, для оптимизатора, перечитывающего на
каждый прогон, — сборщик мусора задохнётся. Формат готов: добавить чтение
в `Float64Array` поверх существующего `decodeRange`.

### Браузерный кэш истории
Квадратичная запись: вся серия одной записью IndexedDB, переписывается целиком
на каждую страницу. Плюс в кэш попадает недоформированная последняя свеча и
остаётся там навсегда с заниженными high/low/volume. Используется только
вкладкой «Тестер»; для CLI есть отдельное хранилище на диске.

## Методология и отчёты

### Скользящие окна перекрываются
Доля прибыльных окон считается с шагом меньше длины окна, поэтому четырнадцать
окон — это не четырнадцать независимых наблюдений. «71% прибыльных месяцев»
звучит статистически весомее, чем есть на самом деле. Шаг настраивается;
нужно либо считать по непересекающимся окнам, либо честно указывать
эффективное число независимых наблюдений.

### Дыры в данных не останавливают прогон
При покрытии ниже порога печатается предупреждение, но прогон идёт. Стратегия
не видит, что между барами провал, и торгует через него как через норму.

### Кэш свечей между прогонами
Каждый прогон читает свечи с диска заново. Для перебора сотен комбинаций по
одному диапазону нужен кэш по ключу диапазона, иначе диск станет узким местом
раньше, чем расчёт.

## Мелочи

- **Роль maker/taker фиксируется по бару размещения.** Если к бару исполнения
  рынок ушёл, лимитка, бывшая маркетабельной, реально встала бы в книгу
  мейкером. Погрешность в одну комиссию, изредка.
- **`onBar` не вызывается для бара 0**, эквити-серия начинается со второго
  бара. Стратегия теряет один бар, статистика — одну точку.
- **`avgHoldSec` в статистике всегда 0** — `PaperTrade` не хранит время
  открытия.
- **Ретрай на `EPERM` при переименовании файла.** На Windows атомарная запись
  датасета может упасть, если файл держит антивирус. Наблюдалось один раз на
  загрузке ETHUSDT: остался `.json.tmp`, месяц завис в состоянии `trailing`.
  Лечится повторным запуском, но ретрая в коде нет.
- **Отчёт о качестве данных не отличает** «биржа не отдала бар» от «мы не
  докачали».
- **`scripts/tsHooks.mjs` — костыль резолва.** Node стрипает типы, но не
  резолвит импорты без расширения, под которые написана половина `src/lib`.
  Хук доразрешает `.ts` после штатного провала. Сломается, если в цепочку
  импортов бэктеста попадёт `.tsx`.
- **Шум в stderr при CLI-прогоне:** цепочка `registry → gridBot → eventBus →
  store` тянет zustand с persist, который в node ругается на отсутствие
  localStorage на каждый лог.
